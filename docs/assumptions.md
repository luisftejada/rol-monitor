# Rules assumptions

When the corpus is ambiguous, or a `beneficio_resumen` is truncated (many feat
summaries end in `…`), we implement the mechanically obvious reading and record it
here rather than guessing silently.

Format: one entry per assumption, newest first.

| Date | Area | Assumption | Rationale |
| ---- | ---- | ---------- | --------- |
| 2026-08-09 | Racial weapon familiarity | Five races carry it, and nothing consulted the race at all: `_is_proficient` built its haystack from class proficiency lines only, so an elf was told they could not use an elven curve blade. It is two mechanics, and conflating them is the trap. **Named weapons** (`competencias_armas.armas`) are proficiencies outright — an elf wizard *can* hold a rapier, which no wizard class line allows. **A word** (`competencias_armas.palabras`) makes any weapon carrying it count as *martial*: the elven curve blade stops being exotic, and it still takes a class with martial weapons to swing it. So the elf fighter is proficient and the elf wizard is not. Six exotic weapons in the catalog carry a gentilic, one race each, pinned by a contract test. | Modelling "cuentan como marciales" as a proficiency would arm every elf wizard with a curve blade. The word is stored in both genders (`élfico`, `élfica`) because the manual names one form and Spanish weapon names inflect — explicit data beats a clever stem match nobody can audit. |
| 2026-08-09 | Two corrected familiarity traits | `Enano` listed "hacha de guerra enana y urgrosh enano" where the manual (p. 22) says battleaxe, heavy pick and warhammer; `Semiorco` listed "hacha de guerra y espadón" where the manual (p. 27) says greataxe and falchion. Both fixed and pinned. | The dwarf one was consequential rather than cosmetic: it granted two *exotic* weapons outright that the manual only makes martial, so a dwarf wizard could swing a waraxe. Found by cross-checking every race's paragraph while implementing the rule — the same sweep that caught the cleric's armour. |
| 2026-08-09 | Every skill is derived, not just the invested ones | `/derive` now returns all 35 skills instead of only those with ranks, a misc modifier or a feat naming them. A GM rolls Percepción at 0 ranks constantly, and the editor shows a line per skill: without a derived line the ability modifier for those rows would have to be computed in TypeScript, which is the one thing the layering forbids. The untrained-use *warning* is gated on a new `SkillState.is_tracked` — true only when the character put something into the skill — because a barbarian who never took Descifrar escritura has not made a mistake. The per-line `untrained_violation` flag still reports on every row. | Warning on bare absence would have fired two dozen times per character, which is how a useful warning becomes noise nobody reads. |
| 2026-08-09 | A skill's three columns come from the domain | `SkillResult` carries `ranks`, `ability_modifier` and `other_modifiers`, guaranteed to sum to the total (a golden test asserts it for every fixture). "Others" is a *residue* — total minus the two named parts — rather than a filter over the breakdown, so nothing can fall between the columns. The two named parts are recovered from the applied list **by object identity**, not by matching their label: labels are display strings and would break the split the moment one was reworded. | The frontend must show four numbers per skill and may not add up any of them. A partition that can silently lose a modifier is worse than no partition, since the columns would quietly stop reconciling with the total the GM reads. |
| 2026-08-09 | Breakdown labels name abilities in Spanish | `Ability.label` gives "Fuerza", "Destreza"… where three call sites used the enum's *member name* and produced "Str", "Dex", "Cha". | The skills tooltip put those beside "Habilidad de clase" and "Cota de escamas", where an English identifier reads as a bug. Breakdown labels are data in the corpus' language, like every other source name; the English-code rule is about identifiers, not about strings the GM reads. |
| 2026-08-09 | Automatic proficiencies: armour is a feat, weapons are not | The five armour/shield proficiencies are now granted as `fija` slots by the eight classes that get them (24 entries, p. 121-122). The two weapon proficiencies are **not**, and this is the manual's own distinction rather than a judgement call: armour reads *"disponen automáticamente de X **como dote adicional**"*, while weapons read *"tienen automáticamente competencia con todas las armas sencillas"* and *"son competentes con todas las armas marciales"* — proficiency without the feat. So `clases.<slug>.competencias` stays the source of truth for weapons, where all the irregular detail lives (the cleric's favoured weapon, the wizard's five items, the druid's non-metallic restriction), and the feats carry armour and shields, where the prerequisite chain needed them. | A level-6 fighter — proficient with every shield by class — was told they were ineligible for all ten feats gated on `Competencia con escudo`, because eligibility matches prerequisites against *feat names* and prose is invisible to it. Granting Martial Weapon Proficiency as a feat would have been worse than useless: it applies to one chosen weapon type, so counting it towards a prerequisite would license builds the rules forbid. |
| 2026-08-09 | Two corrected proficiency lines | `explorador` said "armaduras ligeras" where the manual says ligeras **e intermedias** (p. 55, confirmed by the feat's own Especial on p. 121), and `clerigo` said "todas las armaduras" where the manual grants only light and medium (p. 40, confirmed by heavy armour's Especial listing only fighters and paladins). Both fixed, both pinned by a test. | The ranger error had been reported twice and carried as "harmless today" — it stopped being harmless the moment armour proficiency became a feat, since the ranger would have been short one. The cleric error was found by this same cross-check and would have handed every cleric full plate. |
| 2026-08-08 | Prestige-class bonus feats | Two of the three prestige classes the manual sweep found now declare `dotes_adicionales`: `caballero_arcano` (a Combat feat at 1, 5 and 9, p. 380 — and unlike the monk's it *must* meet its prerequisites, which the corpus records as a `nota`) and `discipulo_del_dragon` (2, 5 and 8, p. 387). No code changed to make them count: prestige classes already went through the same `_feat_slots` mapping, which is what "the container exists and is empty" meant. `maestro_del_saber` is deliberately left out — its two feats hang off a *secret*, a choice the sheet does not model, so it belongs with domains, arcane schools and rogue talents rather than with the level-gated slots. | The three were listed in `docs/corpus/INVENTARIO_dotes_fuera_de_progresion.md` as the cheapest corpus errand. A contract test now pins which prestige classes grant feats and at which levels, so a corpus regeneration that drops them fails loudly instead of quietly shrinking a budget. |
| 2026-08-08 | Pinning a branch of a restricted list | A slot may name one branch of a list keyed by a choice: `lista: dotes_de_linaje_hechicero` + `opcion: draconico`. The dragon disciple draws from the draconic bloodline *by definition*, so its list resolves to the exact 7 feats rather than the 40-feat union across bloodlines that a sorcerer's own slot still gets. Resolved lists are filed under `key/branch`, because a sorcerer 7 / dragon disciple 2 references both and one bare key would let the wider list overwrite the narrower. A branch the corpus does not have resolves to *nothing*, never to the union. | The inventory noted the draconic list already exists and must not be duplicated, so pointing at it needed a way to say which branch. Falling back to the union on a typo would hide a corpus error behind a plausible answer — an empty picker is at least visibly wrong. This is also the mechanism that will narrow the ranger's style and the sorcerer's bloodline the day the sheet models those choices. |
| 2026-08-08 | Power Attack's manoeuvre penalty | The corpus penalises attacks *and* `bmc` in the same breath, but only the attack half reached the sheet: `Ataque poderoso` is weapon-scoped, so it is never offered as a stance, and a weapon line carried nothing but attack and damage. The line now carries a CMB of its own — `AttackRoutine.cmb`, present only when the line changes it — resolved through the same `derive_cmb` as the character's, so it arrives with a full breakdown rather than as a bare number. The character's own CMB is left untouched: the penalty is only paid while that line is the one in use. A feat that is *also* offered as a stance (`Pericia en combate`, the only other holder of `bmc`) leaves its CMB penalty to the stance, or ticking the box and reading the line would charge it twice. | Power Attack is the feat most likely to be running when a GM calls for a bull rush, and the sheet was overstating that CMB by up to 6. Putting the penalty on the character instead would apply it to a round in which the line was never used, which is the same defect in the other direction. |
| 2026-08-08 | Restricted feat lists | The corpus states its four restricted lists in four different shapes — a type filter plus extras (wizard), level to feats (monk), style to level to feats (ranger), bloodline to feats (sorcerer). They are resolved to plain feat names in `RulesRepository.restricted_feat_list`, keyed by level so a slot taken later sees everything unlocked up to it. Where the list depends on a choice the sheet does not model — the ranger's combat style, the sorcerer's bloodline — the union across branches is returned, which is *wider than the truth*, so the corpus' own caveat is shown alongside it. | Walking four shapes in TypeScript would be rules logic in the wrong layer, and the shapes would leak into the frontend. Note that YAML parses `2:` as an int, not a string: the first version of the level filter never fired, and every list came back at full size. |
| 2026-08-08 | Feat budget | Slots come from three sources and are summed by the backend, never by the frontend: `avance.niveles_con_dote` for every character, `clases.<slug>.dotes_adicionales` gated on the level *in that class*, and `razas[].dotes_adicionales`. A `fija` slot is granted outright and costs no choice — a level-1 monk picks one feat, not three — and granted feats are added to the character's effective list even when nobody typed them, which is what makes a monk proficient with their own fists. Going over budget is a warning, never a block. | Gating class slots on the character's total level would give a cleric 4 / fighter 8 the fighter's level-8 feat, a silent multiclass bug. Counting fixed feats as choices would overstate the budget for every monk, wizard and sorcerer. |
| 2026-08-07 | Mounted feats | `Ataque al galope`, `Carga impetuosa` and `Desmontar jinete` (activation `accion_de_carga_montado`) are deliberately left unmodelled: they need a mount with its own speed and charge rules, which no sheet holds. The provisional plan is to render them as stances. A test pins the set and asserts they contribute nothing, so implementing them forces this entry to be revisited. | Charging while mounted is not expressible as a modifier on the rider's sheet alone, and guessing at it would put numbers on the card that the rules do not support. |
| 2026-08-07 | Bleeding Critical | `Crítico sangrante` is the one critical feat offered as a stance rather than only a note: its 2d6 keeps running on the target every round, so the GM has to keep applying it, and the toggle is the reminder. It emits no modifier — the damage lands on the opponent, not on the sheet — and its text is shown on screen while active instead of only as a tooltip. Revisit when combat between two sheets is modelled. | The other critical feats resolve on the hit itself and carry nothing between rounds, so a toggle for them would be a switch that never needs turning off. |
| 2026-08-07 | Critical feats | The eight `Crítico X` feats apply a condition to the *target*, not a number to the character, so they are rendered as prose annotations on every line of the weapon rather than as variants or stances. They fire with whatever you are holding, which is why they annotate the base line and all its variants inherit them. The corpus' own "only one critical feat per critical hit" rule is surfaced verbatim, and only when it bites: more than one such feat and no `Maestría con los críticos`. Applying the condition stays manual until the NPC module exists. | Eight variants would differ only by name, since none changes a number. Revisit when combat between two sheets is modelled. |
| 2026-08-07 | Combat Expertise (split feats) | A feat can be both a stance and an attack variant. `Pericia en combate` penalises melee attacks — which only means something per weapon — and raises AC and lowers CMB, which only mean something for the character. Each half is rendered where it can apply, and `is_global_feat_target` keeps them disjoint so neither is counted twice. The tracker carries a note saying the attack half lives on the weapon line, or half the feat looks missing. Purely weapon-scoped feats (`Ataque poderoso`, `Puntería mortal`, `Disparo rápido`) are still excluded from stances: their whole effect is on the line. | The variant previously showed the attack penalty with no sign of the AC bonus that pays for it — the same defect `Disparo rápido` had. The residue this left — Power Attack's CMB penalty, which no stance could carry — was closed on 2026-08-08 by giving the weapon line a CMB of its own; see the top entry. |
| 2026-08-07 | Lunge (feat stances) | `Acometer` changes no attack or damage number — it buys 5 feet of reach for -2 AC — so there is no weapon line to hang it on, yet the GM declares it, so it is not passive. It is modelled as a stance that only appears for characters holding the feat, alongside charging and fighting defensively. A feat qualifies when it is declared, is not weapon-scoped, is not a feat weapon, and touches no attack/damage target; today that is `Acometer`, `Hendedura` and `Gran hendedura`. The -2 comes from the corpus, so no scaling is recomputed. The reach itself is not derived: the sheet has no reach line, and adding one for a single feat would be disproportionate. | Offering a stance for a feat that already produces an attack variant would let the GM apply the same feat twice, which is why the exclusion is part of the classification rather than a hand-kept list. |
| 2026-08-07 | Medusa's Wrath | Modelled as its own weapon line built from `Impacto sin armas`, not as a modifier on a carried weapon: it is a full attack of unarmed strikes, and Pathfinder does not let one full attack mix armed and unarmed. It therefore never combines with the variants of a carried weapon. Its two extra attacks are made at the highest bonus, taken from the corpus modifier (`ataques_adicionales_sin_armas: 2`), not hardcoded. Its situation ("vs. a stunned, flat-footed… opponent") cannot be checked from the sheet, so the line is generated and *labelled* with it rather than hidden or silently applied. | The same mechanism fixed `Disparo rápido`, which was showing its -2 without the extra shot that pays for it. |
| 2026-08-07 | Unarmed proficiency | A character with `Impacto sin arma mejorado` is proficient with unarmed strikes. The monk's `competencias` reads "armas de monje seleccionadas" and never says "sencilla", so the text match gave a monk -4 with their own fists. | Surfaced by the Medusa's Wrath line: an 11th-level monk derived +7 where +11 was right. |
| 2026-08-07 | Vital Strike | The family supersedes rather than stacks: holding `Golpe vital mayor` leaves the other two with *no effect at all*, so they are dropped before variants are generated — not merely prevented from stacking. Its activation (`accion_de_ataque`) forbids a full attack, so its line keeps only the highest attack bonus instead of the iteratives. `SUPERSEDED_FEATS` is an explicit table because the corpus states this in prose; a contract test asserts each entry is backed by a "sustituye" rule naming the replaced feat. | Prerequisites force a character to hold all three, so without supersession a level-16 fighter derived x24 damage dice across eight lines. Prerequisites alone are not the signal: `Combate con dos armas mejorado` also requires its base feat but adds to it. |
| 2026-08-07 | Manyshot | `Disparos múltiples` carries no modifier in the corpus — its mechanic is five lines of prose — so it is keyed by canonical name in `rules/weapon_feats.py`, the same way `domain/conditions.py` keys `estados`. It multiplies the weapon's damage *dice* by 2 on the first attack only; flat damage (Strength, Deadly Aim) is added once, not doubled. The sheet shows the first attack's expression separately, since "2d8 then 1d8" is not a single number. | The alternative is inventing a modifier the data does not contain. Keying by name keeps the mechanic visible and testable, and `Golpe vital` (which *does* declare `dados_dano_arma: x2/x3/x4`) shares the same code path. |
| 2026-08-07 | Stances vs weapon feats | `Ataque poderoso` and `Pericia en combate` were removed from the stance toggles. They belong to a weapon and are rendered as alternative attack lines; leaving the toggles in place would apply them twice. `scale_step` and `power_attack_damage_bonus` went with them: the corpus states the scaling per BAB band, so recomputing it was a second source of truth. The remaining stances are the situational ones — charge, fighting defensively, total defence, flanking, high ground — which no weapon can know about. | A GM who ticks the box *and* reads the Power Attack line would silently double the penalty and the damage. |
| 2026-08-07 | Feat activation | Only feats whose `activacion` is `pasiva` contribute modifiers automatically. Everything else (`opcional_declarada_antes_del_ataque`, `rapida`, `estandar`, …) is declared in play, and `Ataque poderoso` / `Pericia en combate` are already modelled as stance toggles — applying them here as well would double-count them. Declared feats that carry numbers are surfaced as a warning instead. | 42 of the applicable modifiers belong to declared feats. Silently adding a Power Attack penalty to every attack line would corrupt the sheet in a way that is hard to spot. |
| 2026-08-07 | Conditional feat effects | An effect gated by `cuando` applies only when every predicate is decidable from the sheet and holds: `ataque_base`, `dados_de_golpe`, and `rangos_habilidad` (read from the skill the effect targets). Situational predicates — `al_confirmar_critico`, `luchando_defensivamente`, `distancia_pies`, `puntos_de_golpe_actuales`, `tipo_arma`, `nivel_lanzador` — are never assumed true; the effect becomes a note. An effect with prose `condicion` but no `cuando` is treated as situational. | A bonus silently added to every attack is worse than one the GM applies by hand: the first is invisible, the second is deliberate. |
| 2026-08-07 | Feat modifier targets | Of the 83 targets `dotes.esquema_efectos.objetivos` declares, 15 map onto `ModifierTarget` (attack, damage, AC, CMB/CMD, the three saves, initiative, base speed) plus per-skill checks as `SKILL:<slug>`. The other 68 are listed verbatim in `rules/feat_targets.py` as deliberately unmodelled — spell mechanics, mounted combat, per-manoeuvre CMB/CMD, per-grip damage, and per-class resource pools. `parse_feat_target` returns `None` for them rather than raising: an unmodelled target is expected, and the effect is still shown as an informational note rather than summed. | Inventing ~68 enum members for mechanics this PC-combat milestone never derives would trade a small correct core for broad, shallow coverage. Listing them explicitly keeps the contract test able to prove every declared target is classified. |
| 2026-08-07 | Feat skill targets | `prueba_habilidad.<Nombre>` is slugged with the same `slugify` the skills catalog uses, so both sides agree on `SKILL:acrobacias`. `prueba_habilidad.Artesania_o_Profesion_elegida`, `prueba_habilidad_elegida` and `prueba_caracteristica.*` are unmodelled: the first two need the character's `feat_options`, and the sheet derives no ability-check line (the domain's `ABILITY:` target is an ability *score*). | A contract test asserts every named skill exists in `habilidades.lista`, so a misspelling cannot slug into a target no skill ever queries. |
| 2026-08-06 | Feat bonus types | The feats block spells bonus types as ASCII slugs and picks different words from `sistema.tipos_de_bonificador` (`mejora`/`potenciador`, `perspicacia`/`introspección`, `natural`/`armadura natural`, `alquimico`/`alquimia`, `tamano`/`tamaño`, `deflexion`/`deflexión`). `rules/feat_vocabulary.py` translates the feats dialect into `BonusType`; the domain keeps a single vocabulary. `sin_tipo` and `penalizador` both map to untyped, because the engine reads penalties from the sign of the value, not from a type name. | Two vocabularies for one concept would otherwise leak into the stacking engine, and a `mejora` bonus would fail to suppress a `potenciador` one of the same type. |
| 2026-08-06 | Feat modifier values | `multiplicador`, `formula` and `variable` are treated as markers for the *shape* of `valor` ("x2", "2d6", "1_por_dado_de_golpe"), not as bonus types. Translating them raises instead of returning untyped, so they must be dispatched per target. They are used by 15 of 227 feat modifiers but are absent from the corpus' own `esquema_efectos.tipos_bonificador` declaration. | The corpus warns these values cannot be summed. Silently mapping them to untyped would add a multiplier as though it were a flat bonus. |
| 2026-08-03 | Encumbrance | A medium/heavy/over-heavy load acts like medium/heavy armor: max Dex to AC +3 / +1 / +1 and check penalty -3 / -6 / -6. Armor and load do not stack — the more restrictive max-Dex and the worse check penalty apply — but a shield's check penalty is always added. CMD uses the full Dex modifier (not capped). | The corpus gives carrying thresholds via `carga()` but not the derived penalties; these are the standard PF1e encumbrance effects. |
| 2026-08-03 | Speed | Speed under medium/heavy armor or encumbrance uses a lookup (30→20, 20→15, 40→30, …) with a `max(5, floor(base/5)*5 - 5)` fallback for uncommon base speeds. | The corpus stores per-armor reduced-speed strings but not a general rule; the CRB table only fixes 30 and 20. |
| 2026-08-03 | Bonus types | `deflexión` (deflection) is not listed in `sistema.tipos_de_bonificador` but is added to the `BonusType` enum as a standard non-stacking type. The AC formula and the combat-sheet breakdown example both use it. The enum-exhaustiveness test asserts the corpus types are a subset of the enum (so corpus drift still fails), while allowing known standard extras. | Omitting it would force deflection bonuses to be untyped and wrongly stack (e.g. two rings of protection). |
| 2026-08-03 | Multiclass saves | Prestige classes use their own CRB save tables, which do not match the by-type save formula (verified: base classes 0 mismatches, prestige 141). Base saves are therefore sourced from the per-row progression tables, and BAB from the by-type formula (which matches all 21 classes). See ADR 0004. | The by-type formulas are authoritative for BAB everywhere but only for base-class saves; prestige save rows are the only correct source. |
| 2026-08-03 | Prestige classes | Three prestige classes ship with incomplete `progresion` in the vendored corpus: `cronista_pathfinder` and `danzarin_sombrio` have 0 rows, `duelista` has only its level-10 row. The catalog exposes them with `max_level` equal to the highest defined level; requesting a level without a row returns 404. In derivation they contribute BAB (via formula), HP, and skills; missing save contributions are treated as 0 and a `warnings[]` entry is emitted. Nothing is invented. | The corpus is vendored, read-only, and the PC module is the milestone; prestige/NPC support is secondary. We surface what exists rather than inventing missing rows. A data-contract test pins the known-incomplete set so any change is caught. |
